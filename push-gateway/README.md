# Własny push Androida — konfiguracja po buildzie

Kod i testy są lokalnie gotowe. Bez własnego projektu Firebase, klucza serwisowego, rejestracji telefonu oraz wybranego publicznego HTTPS **nie potwierdzono dostarczania powiadomień**. Nie wdrożono usługi, nie ustawiono DNS i nie używano sekretów innych usług.

Gateway przyjmuje `POST /_matrix/push/v1/notify`, wiąże dokładne własne `app_id`, token FCM i losowy nonce. Nonce przechodzi w `device.data.gateway_nonce`, nigdy w URL. Aplikacja ma Android package `pl.personal.chat`; Matrix pusher ma `pl.personal.chat.<deviceID>` (maks. 64 znaki), zgodnie z kodem klienta. Nie przejmuje pusherów oficjalnego Beepera.

## Konfiguracja Firebase — 2026-10-06

Firebase CLI skonfigurowało własny projekt `<firebase-project-id>` i aplikację Android `pl.personal.chat` (Firebase app ID `<firebase-app-id>`). FCM API ma stan ENABLED. Konto `personal-push` ma własną rolę `personalPushSender` z jedynym uprawnieniem `cloudmessaging.messages.create`.

Konfiguracja Android i klucz serwerowy są w prywatnym katalogu `~/.config/personal-chat/firebase/` z uprawnieniami 700/600. Ignorowany `android/app/google-services.json` jest dowiązaniem do prywatnego pliku. Klient używa przypiętego `fcm_shared_isolate` 3.0.0 i aktywnego `FcmPushService`; FCM włączamy tylko na Androidzie. Prywatny `gateway.local.json` służy do kontroli konfiguracji, ma pustą listę urządzeń.

Brama została wdrożona pod `https://push.example.org/_matrix/push/v1/notify`. Nginx publikuje tylko tę ścieżkę przez HTTPS; port 80 służy wyłącznie ACME. Systemd uruchamia gateway jako `personalpush` na loopback 8088. Certyfikat Let’s Encrypt ma timer odnowienia i hook przeładowania Nginx. `prepare_credentials.py` kopiuje chronione credentials systemd (na tym hoście 0440) do prywatnego RuntimeDirectory jako pliki 0600, zachowując kontrolę owner-only w gateway.

Rejestracje są nadal puste, nie ma potwierdzonego odbioru na telefonie. Pozostają rejestracja urządzenia i fizyczne testy. Szczegóły wdrożenia: `../../docs/personal-push-deployment-2026-10-06.md`.

## Kroki J

| Krok | Co przygotować / wykonać | Dowód odbioru |
|---|---|---|
| 1. Własny projekt | W Firebase Console wybierz własny projekt i dodaj Android app o package **`pl.personal.chat`**. Nie używaj projektu FluffyChat ani konfiguracji oficjalnego Beepera. | `google-services.json` zawiera ten package i wybrany `project_id`. |
| 2. Konfiguracja Android | Zachowaj plik poza repo, np. `~/.config/personal-chat/firebase/google-services.json`, z mode `600`. Uruchom `setup.py check-android --file ABSOLUTE_PATH --project-id OWN_PROJECT_ID`. | Helper wypisuje tylko potwierdzenie zgodności, bez kluczy. |
| 3. Build z FCM | W katalogu klienta podłącz własny, ignorowany `android/app/google-services.json`; włącz przypięty `fcm_shared_isolate` 3.0.0 i natywny `FcmPushService`, następnie zbuduj własny release APK. Skrypt upstream `scripts/add-firebase-messaging.sh` pobiera nieprzypiętą zależność i edytuje pliki — nie uruchamiaj go w ciemno. | Test manifestu APK, własny podpis i runtime `firebaseEnabled`; faktyczny token telefonu, bez drukowania w logach. |
| 4. Klucz serwerowy | W tym samym projekcie włącz Firebase Cloud Messaging API. Utwórz dedykowane service account tylko dla tego projektu, z uprawnieniem `cloudmessaging.messages.create` (custom role) albo projektową rolą `roles/firebasecloudmessaging.admin`. Zapisz JSON jako `/etc/personal-push/fcm-service-account.json`, root `600`. | Plik ma `type=service_account`, ten sam `project_id` i Google OAuth token URI; gateway blokuje inny projekt/endpoint. |
| 5. Lokalna usługa | Utwórz osobnego system user `personalpush`, katalog `/opt/personal-push-gateway`, Python 3.10+ oraz lokalny venv. `pip install -r requirements.txt` instaluje przypięte `google-auth`. Kopię `config.example.json` zapisz poza repo jako `/etc/personal-push/config.json`, root `600`; zmień tylko własny project ID i świadomie wybrane limity. | `--check` sprawdza pliki bez wywołania Google. Systemd `LoadCredential` udostępnia kopie `400` tylko tej usłudze. |
| 6. Telefon | Uzyskaj token FCM i dokładny własny pusher app ID z własnej aplikacji przez prywatny ekran konfiguracji, bez wklejania ich do czatu ani logów. Użyj `setup.py register --config PRIVATE_CONFIG --app-id OWN_PUSHER_APP_ID --nonce-file NEW_PRIVATE_PATH`; token i opcjonalny nonce wpiszesz w ukrytych promptach. | Rejestracja pojawia się tylko w prywatnym config; helper nie wywołuje żadnego API. |
| 7. HTTPS | Z J wybierz domenę. Istniejący reverse proxy udostępnia wyłącznie `/_matrix/push/v1/notify` przez poprawny TLS, przekierowując na `127.0.0.1:8088`. `nginx.example.conf` jest szablonem; nie instaluj drugiego proxy na portach istniejącego Traefika. | Uwierzytelniona konfiguracja sieci/usługi i zewnętrzny test TLS. Nie otwieraj portu 8088 ani publicznego chat API. |
| 8. Pusher aplikacji | W **Personal → Konfiguracja powiadomień** wpisz pełny `https://OWN_HOST/_matrix/push/v1/notify` oraz nonce z prywatnego pliku. Nonce trafia do secure storage. Jawnie przeładuj gateway po zmianie prywatnego config, następnie zarejestruj własny pusher `format=event_id_only`, `data_message=true`, `gateway_nonce=...`. | Ten app ID/token/nonce są zgodne po obu stronach. Zmiana nonce wymaga aktualizacji pushera, nie tylko lokalnego ustawienia. |
| 9. Fizyczny test | Użyj wskazanej bezpiecznej rozmowy: foreground, wygaszony ekran, recent-app swipe, Doze, offline → reconnect i kliknięcie powiadomienia. Force-stop sprawdź osobno jako ograniczenie Androida. | Osobne PASS/FAIL dla token registration, FCM receipt, odszyfrowania i właściwej rozmowy. HTTP 200 `/healthz` nie potwierdza żadnego z nich. |

Nie przekazuj service-account JSON, tokenów lub nonce do asystenta. Metadane `google-services.json` muszą być wbudowane w APK zgodnie z Firebase; uprzywilejowany klucz serwerowy pozostaje na VPS. Nie commituj żadnego z tych plików. Wydanie debug bez FCM nadal nie jest testem własnego push.

## Przypomnienia, gdy klient jest zamknięty

Homeserver może nie wypchnąć do klienta eventu własnego nadawcy. Dla potwierdzonego `reminder.result` worker może użyć osobnego lokalnego `POST http://127.0.0.1:8088/internal/reminder`. Kontrakt to dokładnie `{hintId, emittedAt}`: stabilny nieprzezroczysty SHA-256 identyfikator i UTC ISO8601. Nie ma tam room ID, kontaktu ani treści. Osobny serwerowy bearer jest wymagany; nonce aplikacji nie upoważnia do tego endpointu.

W upoważnionej konfiguracji utwórz sekret `setup.py reminder-key --file /etc/personal-push/reminder-relay.json`. Helper zapisuje `600` i nie drukuje wartości. W prywatnym config dodaj `reminder_credential_file=/run/credentials/personal-push-gateway.service/reminder-relay.json` oraz odkomentuj odpowiadający `LoadCredential` w unit. Ten sam sekret wpisz do chronionego `reminderRelayToken` w credentials workera; jego `reminderRelayUrl` ma być tylko powyższym loopback URL. Nie publikuj wewnętrznej ścieżki w reverse proxy; dołączony proxy udostępnia wyłącznie Matrix notify. Bez tego pliku endpoint jest wyłączony.

Gateway kieruje do zarejestrowanych aktywnych urządzeń jedynie `{personal_wake: "reminder"}`. Android po tym sygnale synchronizuje i odszyfrowuje journal; alert wynika wyłącznie z zaufanego przypomnienia, którego termin minął. Sygnał nie zawiera tekstu powiadomienia i sam nie jest dowodem należnego przypomnienia. Brak rejestracji / same nieważne tokeny zwraca **503 `M_NO_DEVICES`**, z `Retry-After: 300`; worker zachowuje hint i ponawia z backoff. **200** oznacza potwierdzone przyjęcie przez FCM wszystkich zarejestrowanych ważnych urządzeń i trwały zapis dedup. Nie oznacza dostarczenia na ekran. Przy timeoutach / częściowych błędach jest 503, a kolejna próba tego samego hintu omija wcześniej potwierdzone urządzenia. Sam `emittedAt` jest walidowany, bez trwałego wygaszenia zaległego hintu i bez zapisywania osobistych timestampów do logów.

## Uruchomienie i granice

Kod należy skopiować do `/opt/personal-push-gateway` dopiero w upoważnionym wdrożeniu. Z dostępnymi własnymi plikami uruchamiaj `gateway.py --config PRIVATE_CONFIG --check`, a usługę według dołączonego systemd unit. Unit nie czyta `/home`, nie ma uprawnień roota i zapisuje tylko własny state directory. Lokalny endpoint zdrowia to `/healthz`; nie jest publikowany w szablonie proxy. Konfiguracja i credentials są niejawne; przykładowy config ma pustą listę rejestracji i nie jest gotowym działającym relayem.

Do FCM trafiają tylko `event_id`, `room_id`, JSON `counts` i puste `devices`. SDK `PushNotification.fromJson` obsługuje stringi JSON, a listener `fcm_shared_isolate` rozpakowuje `message.data`. Gateway nigdy nie przekazuje treści, nazw, `default_payload`, nonce ani listy pushkeys w danych wiadomości. Google nadal widzi token docelowego telefonu, **surowe nieprzezroczyste identyfikatory Matrix pokoju i eventu**, liczniki i metadane transportu. To minimalizacja danych; E2EE wiadomości nie ukrywa tej informacji o ruchu. Payload nie zawiera OS notification/title/body; własna aplikacja pokazuje ogólny alert i pobiera treść po autoryzacji.

Obecny minimalny routing pasuje do jednego Matrix account obsługującego wszystkie mosty. Puste `devices` powoduje wybór pierwszego lokalnego klienta. Obsługa kilku kont wymaga osobnego mapowania nieprzezroczystego route ID na lokalnego klienta; nie przedstawiaj tego jako zakończonej zgodności wielu kont. Ta usługa jest Android/FCM; nie zapewnia powiadomień po **Quit** aplikacji macOS ani APNs.

Potwierdzone wysyłki są deduplikowane przez maksymalnie 24 godziny / 20 tys. rekordów. Na dysku zostają tylko skróty token/event/room oraz czasy — bez wiadomości i identyfikatorów źródłowych. Utrata odpowiedzi FCM jest nieustalona: gateway odpowiada `503` z `Retry-After`, żeby homeserver ponowił; klient musi także tłumić duplikaty według event ID. Nie ma obietnicy exactly-once ani gwarancji dostarczenia przez FCM. Transient/IAM/błędny projekt nie usuwa pusherów; dopiero strukturalne `UNREGISTERED` lub `SENDER_ID_MISMATCH` trafiają do `rejected`. Rejestrację odświeżonego tokena trzeba dodać do prywatnego config przed ponownym ustawieniem pushera.

## Weryfikacja bez kont i kosztów

`python3 -W error::ResourceWarning -m unittest discover -s push-gateway/tests -v` w katalogu repo sprawdza prywatność payloadu, nonce/rejestrację, walidację przed side effects, dedup przy współbieżności/restartach, rate limit, nieprawidłowe tokeny, transient `503`, kontrakt HTTP, przypomnienia i ochronę config. Publisher jest wstrzykniętą atrapą; żaden test nie wysyła do FCM. W venv z `requirements.txt` uruchamia się także test rzeczywistego signera `google-auth` z syntetycznym kluczem i zamockowanymi OAuth/FCM endpointami. Całe **15 testów PASS** w takim izolowanym venv; bez zależności test auth jest jawnie pomijany. `python3 -m py_compile push-gateway/gateway.py push-gateway/setup.py` sprawdza składnię. Testy nie dowodzą fizycznego push ani zgodności IAM/TLS/Doze.
